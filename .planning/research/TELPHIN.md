# Телфин: исследование API и условия полной синхронизации

Дата проверки: 2026-11-11. Роль: GSD project researcher. Статус: документация изучена; запросы к реальному аккаунту не выполнялись. Подтверждённые возможности API имеют HIGH confidence по официальным источникам; поведение конкретной АТС требует spike. Архитектурные рекомендации ниже — проектные решения, а не обещания провайдера.

## Вывод для дорожной карты

Первый результат разработки — воспроизводимая выгрузка истории всех доступных вызовов выбранной АТС с подтверждённой полнотой за заданный период. Список аудиозаписей не может служить списком звонков: пропущенные вызовы и разговоры без записи обязаны попасть в сервис. Исторический импорт и регулярная сверка нужны даже при подключённых webhooks.

«Все звонки» в интерфейсе означает все доступные через выданные права записи истории в заявленном диапазоне. Система должна явно показывать диапазон, ограничения доступа, дату последней сверки и незавершённые окна импорта. Отсутствие старых строк само по себе не доказывает, что звонков не было.

## 1. Авторизация и права — подтверждено

Документация описывает public / authorization_code, trusted / client_credentials и password_credentials / password. Trusted работает от имени создавшего его пользователя. Минимальный уровень приложения Call API разрешает GET доступных пользователю ресурсов и регистрацию call events; уровень All не следует требовать по умолчанию. Пользователь read_only ограничивает приложение GET-запросами, что влияет на установку webhooks. [Создание приложений](https://ringme-confluence.atlassian.net/wiki/spaces/Ringme/pages/1901920410).

Для trusted: `POST https://<hostname>/oauth/token`, тело form-urlencoded с `grant_type=client_credentials`, `client_id`, `client_secret`. Ответ содержит `access_token`, `token_type`, `expires_in`. При истечении или отказе токена запрашивается новый client_credentials token; не надо предполагать наличие refresh token у trusted. [Trusted OAuth](https://ringme-confluence.atlassian.net/wiki/spaces/Ringme/pages/1981874187).

Базовый путь REST — `/api/ver1.0/`; токен передаётся через Bearer Authorization. [Структура API](https://ringme-confluence.atlassian.net/wiki/spaces/Ringme/pages/1901920541/REST%2BAPI).

Доступность всей АТС зависит от уровня пользователя: клиент, группа номеров или один номер. Для обещания всей истории нужен проверенный доступ уровня клиента. [Пользователи и полномочия](https://ringme-confluence.atlassian.net/wiki/spaces/Ringme/pages/1901920377).

Рекомендация: для первого внутреннего подключения использовать trusted с минимальными правами; предусмотреть отдельный OAuth-flow для будущих компаний. Проверка подключения должна возвращать доступный scope и диагностировать ограниченный охват, а не просто сохранять «успешно». Один координатор обновляет токен для соединения; параллельные workers не устраивают повторную авторизацию одновременно. После одного повторного grant и повторного 401 задача переходит в состояние `reauthorization_required`.

## 2. История, страницы и составные части — подтверждено

Основные методы:

- `GET /client/{client_id}/call_history/` — история с вложенным `cdr`.
- `GET /client/{client_id}/call_history/{call_uuid}` — отдельный вызов; документирован также `call_month` для ускорения поиска.

Есть параметры `start_datetime`, `end_datetime`, `page`, `per_page`, `order` и фильтры по направлению, номерам, результату, длительности. Ответ содержит `page`, `per_page`, `order`, `call_history`. Пример `per_page=100000` не устанавливает гарантированный предел страницы.

История объединяет весь вызов и его части. Уровни имеют различную семантику `result`: `answered elsewhere` относится к CDR, а `bridged` — к вызову. Времена описаны как UTC. [История вызовов](https://ringme-confluence.atlassian.net/wiki/spaces/Ringme/pages/1901921310/call_history).

`GET /client/{client_id}/calls/` возвращает вызовы без массива CDR и описан как более быстрый вариант, когда детали плеч не требуются. [Calls](https://ringme-confluence.atlassian.net/wiki/spaces/Ringme/pages/1930231842/calls).

CDR поддерживает `flow=in/out/transfer`, содержит `calls_result`, `record_uuid`, `record_file_size`, `storage_url`; идентификатор и размер записи могут быть null. [Составные части](https://ringme-confluence.atlassian.net/wiki/spaces/Ringme/pages/1901921567/cdr).

Рекомендация: начинать с call_history как одного проверяемого контракта. Оптимизацию calls → выборочная загрузка CDR вводить по измерениям. Хранить сырой ответ с ограниченным сроком хранения, нормализованный логический звонок, отдельные плечи и отдельные аудиозаписи. Идемпотентность строить в пределах организации, соединения и provider call UUID; точную кардинальность строк и UUID проверить на переводах. Идентификатор CDR нельзя выдумывать: проверить фактический API, затем определить ключ плеча и обработку его обновлений.

Нельзя помечать логический звонок пропущенным только потому, что один сотрудник не ответил. Очередь, IVR, ответ другого сотрудника и перевод должны складываться в один понятный маршрут звонка.

## 3. Ограничения запросов — подтверждено

Телфин требует `Accept-Encoding: gzip`. Лимиты действуют на час, учитывают приложения одного клиента; персональные ограничения приложения возможны дополнительно. Заголовки: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`; последний содержит секунды до сброса. При 429 `rate_limit_exceeded` нужно дождаться сброса счётчика. Для `/oauth` и `/login` отдельно указаны 20 запросов/с и 6 одновременных соединений. Фиксированного общего бюджета, одинакового для всех аккаунтов, документация не задаёт. [Правила запросов](https://ringme-confluence.atlassian.net/wiki/spaces/Ringme/pages/1901920568/API).

Рекомендация: один бюджет запросов для всех задач одного подключения, приоритет текущей сверки перед глубоким backfill; сохранять `next_attempt_at`, не держать процесс в sleep на час. Соблюдать Reset, учитывать Retry-After при наличии, применять jitter и ограничение числа попыток. 403 должен показываться как проблема прав, а не бесконечно повторяться. 5xx/сетевая ошибка не должны продвигать checkpoint.

## 4. Аудиозаписи — подтверждено

`GET /client/{client_id}/record/` получает записи за диапазон. Для списка записей `end_datetime` ограничен последним днём месяца, следующего за месяцем `start_datetime`; большой период разбивается. Есть `GET /client/{client_id}/record/{record_uuid}` для файла и `GET /client/{client_id}/record/{record_uuid}/storage_url/` для ссылки на внешнее хранилище. Документация описывает ссылку хранилища как постоянную и не требующую авторизации. Статистика доступна через `/record/stats/`. [Записи разговоров](https://ringme-confluence.atlassian.net/wiki/spaces/Ringme/pages/1901921281/record).

Рекомендация: постоянную ссылку считать секретом доступа, не писать её в общие логи и не публиковать в карточке/CRM. Отдавать собственный авторизованный playback endpoint или короткоживущую ссылку своего хранилища. Downloader проверяет разрешённые домены, редиректы и адреса назначения, ограничивает размер/время скачивания, сохраняет checksum и MIME. Доступ к файлу проверяется по организации и роли. Наличие metadata не доказывает готовность файла: отдельно различать `not_recorded`, `pending`, `downloaded`, `unavailable`, `failed`. Причины и политика повторов документируются после spike.

## 5. Webhooks — подтверждено

Уведомления предусмотрены для dial-in, dial-out, answer, hangup. [Обзор событий](https://ringme-confluence.atlassian.net/wiki/spaces/Ringme/pages/2039742469).

Формат данных события — form-urlencoded. `CallID` связывает события всего вызова и не меняется при переводе; `SubCallID` различает части. `RecID` соответствует `record_uuid`; `EventTime` и длительности событий выражены в микросекундах. У IVR отсутствует answer, очередь создаёт собственные входящие события и исходящие события обзвона агентов. Число подписок ограничено. [События внутреннего номера](https://ringme-confluence.atlassian.net/wiki/spaces/Ringme/pages/1901921397/extension%2B...%2Bevent).

Рекомендация: webhook сначала надёжно сохраняется в inbox, быстро подтверждается и затем обрабатывается worker. Дубликаты и нарушенный порядок допустимы; финальные данные сверяются по REST. Механизм подписи, retries и timeout провайдера в изученных страницах не установлен: не утверждать, что HMAC существует. В spike подтвердить доступный способ аутентификации; до этого считать payload недоверенным, применять отдельный случайный URL-токен, ограничения размера/частоты, валидацию и сверку call ID через API. Схему защитного URL также проверить на поддержку провайдера.

## 6. Speech-to-text Телфина — отдельная возможность

Официальная страница описывает voice helper и события с распознанным текстом во время разговора; нужна включённая администратором функция `speech_to_text`. Это не доказательство наличия готовой исторической расшифровки каждого импортированного звонка. [Speech-to-text](https://ringme-confluence.atlassian.net/wiki/spaces/Ringme/pages/1901921700/speech%2Bto%2Btext).

Рекомендация: независимый ASR adapter после скачивания аудио. Возможность Телфина оценить дополнительным spike, не делать её обязательным условием анализа истории.

## 7. Обязательный spike до реализации промышленного синка

Без секретов в отчёте сохранить обезличенные fixtures и `provider-contract.md` с результатами:

1. Проверить hostname, получение токена, определение client_id и уровень пользователя. Не принимать client_id из браузера без проверки принадлежности.
2. Выбрать известный оператору период с входящим, исходящим, пропущенным, переводом через очередь, внутренним звонком и звонком без записи. Сравнить историю API и кабинет.
3. Установить фактический предел per_page, начальный номер страницы, критерий конца, доступную сортировку и поведение при новых звонках во время обхода. Не полагаться на отсутствие `total`.
4. Проверить допустимую длину интервала истории отдельно от ограничения списка записей; включённость обеих временных границ, формат и точность timestamps, звонки через полночь/месяц. До подтверждения обходить небольшими окнами с перекрытием и дедупликацией.
5. Проверить cardinality call_uuid/плеч, соответствие webhook CallID истории, устойчивый ключ CDR, окончательность result и позднее появление записи.
6. Проверить доступную глубину истории и аудио, поведение 404/403 и отсутствие записи. Не интерпретировать это автоматически как удалённый звонок.
7. Проверить MIME/codec, mono/stereo и фактическую привязку каналов к участникам; не обещать двухканальную запись до пробы.
8. Считать реальные RateLimit headers с безопасными редактированными примерами; установить бюджеты backfill и polling без искусственного исчерпания лимита.
9. В тестовом подключении проверить установку/удаление только собственных webhook-подписок, доставку/дубликаты/повторы/аутентификацию. Production конфигурацию АТС не менять в ходе исследования без отдельной задачи.

Если реального доступа нет, контрактные тесты делаются по fixtures документации с пометкой `unverified-provider-contract`; фазу получения всех реальных звонков не отмечать завершённой.

## 8. Предлагаемый алгоритм синхронизации

Это проектный алгоритм, а не описание гарантированной согласованности API:

1. Записать immutable scope импорта: организация, соединение, нужный период, UTC, перечень включённых направлений. На первом импорте не фильтровать по наличию записи, результату или минимальной длительности.
2. Создать durable окна фиксированного диапазона. Зафиксировать верхнюю границу перед обходом, читать страницы с проверенным размером, сохранять upsert и checkpoint одной транзакцией.
3. Повторить окна с перекрытием; вести `observed_at`, хеш payload и дату сверки. Временные окна, не отвечающие проверенному контракту, дробить, а не молча обрезать.
4. Отдельный scheduler проверяет актуальную историю и ранее незавершённые звонки, поздние изменения и записи. Webhooks сокращают задержку, polling восстанавливает пропуски.
5. Публиковать в UI/import report: requested period, scanned windows, unresolved windows, imported calls/legs, duplicates, recording states, last successful reconciliation. Только проверенные окна помечать complete.
6. Непрочитанные интервалы не позволяют уверенно утверждать «первичное обращение» или «не перезвонили». Для таких классификаций возвращать `unknown` либо ограничение «в доступной истории».

## 9. Проверка готовности синка

| Сценарий | Ожидаемый результат |
|---|---|
| Повтор одного импорта | Те же логические звонки без дублей; изменения провайдера обновлены |
| Более двух полных страниц, несколько одинаковых timestamps | Ни один call UUID не теряется; конец обхода определён проверенным контрактом |
| Crash после получения страницы/до commit и после commit | Resume не пропускает данные и не создаёт дублей |
| 401 и параллельные workers | Один повторный grant; bounded retry; корректное состояние подключения |
| 429 с Reset | Следующая попытка отложена; checkpoint не перепрыгивает окно |
| Поздний hangup/изменившийся result | Reconciliation обновляет звонок и зависимые статусы |
| Пропущенное плечо, затем ответ другого агента | Один отвеченный звонок; ложного пропущенного нет |
| Поздняя аудиозапись/звонок без записи | Метаданные сохранены в обоих случаях; ASR ждёт только пригодное аудио |
| Duplicate/out-of-order webhook и утрата webhook | Inbox идемпотентен; REST-сверка восстанавливает историю |
| Два подключения/организации с одинаковыми ID | Изоляция данных, задач, медиа и токенов |
| UTC граница месяца и местная зона | Отображение корректно; окна не теряют пограничные вызовы |
| Недоступный старый интервал | Импорт показывает неполный охват; первичность остаётся неизвестной |

Для правила «пропущен и не перезвонили через N часов» уже в модели заложить отличия попытки и состоявшегося контакта. Неуспешный исходящий может означать «пытались перезвонить», но не «связались». Повторный входящий с ответом также может закрыть проблему; расписание/рабочие часы и связь с контактом определяются продуктовой настройкой.

## 10. amoCRM и Google Sheets: ограничения для последующих фаз

amoCRM требует адрес конкретного аккаунта и безопасное хранение токенов. Документированные лимиты — 7 запросов/с на интеграцию и 50/с на аккаунт; 429 требует ограничения потока, многократные нарушения могут привести к 403. [Рекомендации amoCRM](https://www.amocrm.ru/developers/content/api/recommendations).

Sheets API задаёт раздельные read/write квоты: 300 запросов/мин на проект и 60/мин на пользователя/проект; batch помогает уменьшить число запросов, 429 обрабатывается backoff. [Google Sheets limits](https://developers.google.com/workspace/sheets/api/limits).

Рекомендация: обе интеграции через outbox и durable delivery state; при неопределённом исходе запроса сначала reconciliation, затем повтор. Для CRM хранить связь звонок–контакт–сделка и внешний ID доставки; не выбирать случайную сделку при нескольких совпадениях. Для Sheets использовать стабильный ключ звонка и обновление строки, а не слепой append при каждом retry; порядок/номер строки может изменяться пользователем. Прежде чем разрешать автоматическую смену этапа сделки, отделить предложение модели от подтверждённой команды интеграции и определить конфликт с ручной правкой. Детальные OAuth scopes, endpoints и гарантию идемпотентности исследовать в фазе интеграций.

## Нерешённые вопросы

- Права и настройки конкретной АТС, доступность записи, объём и срок хранения.
- Проверенные пределы и семантика временных окон/пагинации истории.
- Гарантии доставки, аутентификация и повторы webhooks.
- Mono/stereo и точность разделения ролей клиента/менеджера.
- Продуктовая политика: считать ли первичным первый доступный звонок, первый разговор, первый контакт по конкретной услуге или новый эпизод; нельзя решать это одним LLM без истории.

Официальный вход в документацию: [Телфин Open API](https://www.telphin.ru/products/virtual-atc/basic-options/open-api), [Confluence](https://ringme-confluence.atlassian.net/wiki/spaces/Ringme/overview), [API explorer](https://apiproxy.telphin.ru/api/ver1.0/client_api_explorer/). Explorer в текстовом просмотре не раскрыл методы; сведения выше получены из доступных страниц Confluence.
