# Backup, проверка восстановления и журнал удалений

Инструмент работает только с Compose-проектом Phone Platform. Он не читает настройки Bondscan и не подключается к его БД. Runtime `.env.platform` должен быть обычным файлом с правами `0600`; ключ `ENCRYPTION_KEY` хранится отдельно от backup в защищённом хранилище оператора.

## Создание backup

```sh
python3 scripts/backup.py create --directory data/backups/2026-11-11
```

Каталог должен быть новым. На время снимка останавливаются запущенные Compose-сервисы `api` и `worker`, затем запускаются обратно, включая случай частичного сбоя остановки. Другие процессы записи в эту БД на время backup должны быть остановлены оператором. В каталоге создаются приватные `database.dump`, `media.tar.gz` и `manifest.json`; manifest содержит SHA-256 обоих файлов, количество основных сущностей и fingerprint ключа шифрования, без самого ключа. Данные media чувствительны: backup требует защищённого хранения и собственной политики срока удаления.

## Независимый актуальный deletion ledger

Старый backup не знает об удалениях, которые произошли после его создания. Поэтому актуальный журнал удалений нужно сохранять **вне ротации старых backup** и обновлять после удаления данных/retention, а также перед восстановлением:

```sh
python3 scripts/backup.py ledger --ledger-file /private/operator-storage/deletion-ledger-2026-11-11.json
```

Выходной файл должен быть новым. Файл имеет права `0600` и содержит только версию формата, время экспорта, UUID компании/звонка, provider ID и время удаления. Он не содержит записи или текста диалога, но остаётся чувствительным служебным артефактом. В stdout выводится только количество записей. Экспорт не изменяет БД. После восстановления экспорт также учитывает сохранённый `restore_deletion_ledger`, включая записи компаний, которых не было в старом backup.

Для полного катастрофического восстановления нужны исходный ключ шифрования и последний сохранённый ledger, доступные независимо от потерянной БД. Без актуального ledger нельзя гарантировать отсутствие восстановления данных, удалённых после снимка. Наличие одного старого backup такую гарантию не даёт.

## Изолированная проверка

При доступной текущей БД инструмент сам читает её актуальный ledger:

```sh
python3 scripts/backup.py verify --directory data/backups/2026-11-11
```

При потере исходной БД или для воспроизводимой проверки укажите последний приватный экспорт:

```sh
python3 scripts/backup.py verify --directory data/backups/2026-11-11 \
  --deletion-ledger /private/operator-storage/deletion-ledger-2026-11-11.json
```

Проверка не заменяет исходную БД и media volume. Она создаёт случайную отдельную БД `phone_restore_*` и отдельный Docker volume, затем:

1. Проверяет точные checksum entries, SHA-256 файлов и fingerprint ключа. Архив допускает только обычные файлы/каталоги, без links, устройств, FIFO, абсолютных путей или `..`.
2. Восстанавливает дамп, отзывает восстановленные сессии/invite/reset/OAuth grants и сравнивает исходные количества с manifest **до** применения новых удалений.
3. Проверяет UUID/provider ID/время записей ledger. Передаёт JSON как base64-поле `COPY FROM STDIN`: значения не становятся SQL-кодом и не попадают в argv или обычные логи.
4. Сохраняет полный ledger в `restore_deletion_ledger`; переносит записи существующих компаний в рабочие `deletion_tombstones`. Удаляет совпавшие звонки по UUID или provider ID строго в пределах компании, их рекурсивных потомков, связанные jobs/outbox через FK. Ledger сохраняется и блокирует повторный импорт.
5. Разворачивает media в отдельный volume. Один helper-container получает проверенные пути через stdin, удаляет непривязанные к живым ready recordings файлы удалённых звонков и проверяет оставшиеся готовые файлы. Shared physical artifact сохраняется до удаления последней живой ссылки; это отражается как shared_media_retained. Пути обязаны начинаться с UUID соответствующей компании; shell получает их только как данные в кавычках.
6. Проверяет отсутствие совпавших звонков и удалённых media; выводит только агрегированные результаты. Удаляет временную БД и volume, включая случай ошибки.

Для компаний, отсутствующих в старом снимке, ledger остаётся в отдельной таблице без создания фиктивных организаций. Исходная БД читается только для экспорта ledger; все мутации восстановления ограничены случайной отдельной БД.

`verify` — доказательство воспроизводимого восстановления в изоляции, а не команда production cutover. Переключение сервиса на восстановленную БД требует отдельно подготовленного операторского окна и сохранения актуального ledger до возобновления импорта/worker.

## Проверки реализации

```sh
python3 -m unittest discover -s scripts/tests -p test_backup_tools.py -v
```

14 автоматических проверок покрывают checksum/key validation, опасные архивы, приватные файлы, частичную остановку, строгий ledger JSON, безопасную передачу SQL-данных, порядок baseline → replay → media и один helper для множества записей. Дополнительно replay SQL проверен на реальном изолированном PostgreSQL: удалены call/recursive children/provider-ID duplicate и jobs/outbox, другая компания с тем же provider ID сохранена, ledger отсутствующей компании сохранён, повторный replay идемпотентен. Отдельный реальный Docker smoke подтвердил удаление и проверку media с пробелами/специальными символами в имени.

Полный Compose snapshot/restore smoke выполнен:2 организации/4 users/241 documents/9 jobs в baseline,22 ready media references,1 новая deletion ledger entry,5 удалённых после снимка docs. No resurrection=true, shared artifact retained 1; originalDB не менялась, restored sessions/grants отозваны. Агрегаты: `data/eval/backup-verify.json`; это локальное доказательство, без согласованных production RPO/RTO.

## Помощник настройки

Backup не архивирует Docker volume `assistant_auth` с авторизацией Codex. После изолированного restore отзываются сессии/приглашения, capability всех turn/auth attempts, обнуляется подтверждённая авторизация модели, прерываются активные запросы, физически удаляются временные encrypted credentials. Постоянные настройки подключения Телфина сохраняются зашифрованными. Перед использованием помощника нужен новый вход в Codex.

Журнал удалений также применяется к удалённым чатам (включая дочерние сообщения/runs/receipts/credentials) и отдельным временным доступам. Сопоставление provider ID действует только на звонки; UUID и организация — на разрешённые виды документов. Базовые количества проверяются до replay и очистки, поэтому ожидаемое удаление временных данных не маскируется проверкой количества.

## Ожидающие подтверждения регистрации

Изолированный restore отзывает pending emailproofs: version-safeSQL удаляет `registration_challenges`, если такая таблица есть в снимке. Иначе недавний snapshot мог бы оживить уже использованный OTP. Пользователи/компании этой очисткой не меняются. Новый регрессионный тест на настоящей отдельной PG проверяет старую схему, очистку новых proofs и сохранность users/orgs; без DELETE тест падает. При ручном productionrestore оператор применяет тот же отзыв перед запуском API — verify остаётся изолированной проверкой, не productioncutover.
